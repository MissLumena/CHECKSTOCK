# CheckStock — где сейчас товар?

Прототип учёта остатков по фулфилмент-складам (ФФ), резервам FBS и поставкам FBO.
Стек: Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL 16. Фронтенд — один HTML-файл без сборки.

## Быстрый запуск (Python, Windows)

Требуется Python 3.12+. Команды выполняйте из папки проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:DATABASE_URL = "sqlite:///./checkstock.sqlite3"
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте <http://localhost:8000>; API-документация: <http://localhost:8000/docs>.
При первом старте создаются таблицы и начальные данные: склады «Север»/«Юг» и SKU-101..103.
SQLite удобен для локального демо, но не обеспечивает блокировки строк при параллельной работе.
Локальную базу можно сбросить из той же папки командой `python -m app.seed --reset`.

## Запуск с PostgreSQL через Docker

```powershell
docker compose up --build
```

PostgreSQL нужен для проверки реальных блокировок и параллельных операций. Для внешней базы
задайте `DATABASE_URL=postgresql+psycopg://user:pass@host/db` перед запуском Uvicorn.
Сбросить данные PostgreSQL к начальному набору: `docker compose exec app python -m app.seed --reset`.

## Проверки

```powershell
python -m pytest -q
```

По умолчанию тесты используют отдельный файл `checkstock_test.sqlite3` и пересоздают его данные;
рабочая база приложения не затрагивается. Можно указать PostgreSQL через `TEST_DATABASE_URL`.
Набор проверяет 12 сценариев: начальные остатки, FBS/FBO, перемещения, отмены и повторные
подтверждения, дефицит на складе и в целом, мягкое удаление, переименование и идемпотентность.
В складских сценариях дополнительно проверяется баланс `/api/audit`.
Последний прогон этой версии: `12 passed`.

## Модель учёта

* `stock(product, warehouse)` хранит `on_hand` (физически) и `reserved`. **Доступно = on_hand − reserved.**
  CHECK-ограничения в БД: `on_hand ≥ 0`, `0 ≤ reserved ≤ on_hand`. Даже баг в коде не уведёт остаток в минус.
* Товар «в пути» не хранится в остатках, он живёт в документах: `transfers` (ФФ→ФФ, `in_transit→received`)
  и `orders` (FBS: `reserved→shipped|cancelled`, FBO: `in_transit→received`).
* `movements` — журнал только на добавление: товар, штуки, откуда, куда, документ.

| Действие | on_hand | reserved | Где числится |
|---|---|---|---|
| Приход | +N на ФФ | | ФФ |
| Отправка перемещения | −N на ФФ-источнике | | в пути между ФФ |
| Приёмка перемещения | +N на ФФ-получателе | | ФФ |
| Резерв FBS | | +N | ФФ (недоступно) |
| Отправка FBS | −N | −N | в пути к клиенту |
| Отмена резерва | | −N | ФФ (доступно) |
| Отправка FBO | −N | | в пути на склад МП |
| Приёмка FBO | | | склад маркетплейса |

**Инвариант** (`GET /api/audit`, галочка в шапке): сумма приходов по SKU = физически на ФФ +
в пути (ФФ, FBO, FBS) + принято на МП. Если товар «потерялся» или «размножился», это видно сразу.

## Ключевые решения

**Повторное подтверждение не списывает дважды.** Две защиты.
1. Переходы статусов — конечный автомат под `SELECT … FOR UPDATE`: повторная «приёмка»/«отправка» видит
   финальный статус и возвращает `changed: false`, ничего не трогая. Параллельные клики ждут друг друга на блокировке.
2. Создание документов (приход, перемещение, резерв, FBO) принимает заголовок `Idempotency-Key`. Ключ пишется
   в той же транзакции, что и операция; повтор возвращает сохранённый ответ (`replayed: true`). UI держит ключ,
   пока не пришёл ответ сервера, так что повтор при обрыве сети безопасен.

**Нехватка на выбранном ФФ.** Сервис различает два случая:
* `insufficient_at_warehouse` (HTTP 409): на выбранном ФФ мало, но суммарно хватает. В ответе — сколько не хватает и
  на каких ФФ есть доступный остаток. UI предлагает «перевезти N шт из X»; после приёмки операцию можно повторить.
  Остатки автоматически **не** двигаются: решение о перевозке остаётся за менеджером.
* `insufficient_total`: нет и суммарно.

Резерв недоступен и для перемещения/FBO, поэтому товар под FBS нельзя «увезти из-под заказа».

**Удаление ФФ — мягкое.** Склад получает `deleted_at`, строки `stock` и `movements` не трогаются. В «Остатках» и «Складах»
удалённый ФФ виден с пометкой «(удалён)», пока на нём что-то числится. Принять/зарезервировать туда новый товар нельзя,
а вывезти остаток (перемещение, FBO) и отправить/отменить уже сделанные резервы можно. Нельзя удалить ФФ, на который
едет перемещение: иначе товар «завис» бы в пути.

**Что сознательно упрощено.** Нет авторизации. Один магазин. Один SKU на документ. Нет статуса «доставлено клиенту»
(FBS заканчивается на «в пути к клиенту»). Схема создаётся через `create_all`, без миграций. Следующие шаги — Alembic,
многострочные документы, авторизация.

## API

`GET /api/stock · /warehouses · /transfers · /orders · /movements · /audit` ·
`POST /api/receipts · /transfers · /transfers/{id}/receive · /fbs · /fbs/{id}/ship · /fbs/{id}/cancel · /fbo · /fbo/{id}/receive` ·
`POST/PATCH/DELETE /api/warehouses`. Swagger: `/docs`.

## Сценарий демонстрации с пояснением

1. На вкладке «Остатки» покажите начальные количества и зелёную отметку аудита.
2. Попробуйте зарезервировать 2 SKU-103 на «Севере»: там товара нет, но он есть на «Юге».
   UI объяснит дефицит именно на выбранном складе, не перемещая товар автоматически.
3. Создайте перемещение 2 штук с «Юга» на «Север» и примите его. Повторная приёмка не меняет
   остаток; затем резервируйте товар и покажите разницу между физическим, резервным и доступным.
4. Завершите отправкой FBS и проверьте, что аудит остатков по-прежнему сходится.
